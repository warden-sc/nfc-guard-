# 확정 범위 및 개발 기준

기준: 2026-11-11 사용자 전달 회의 결과. [프로젝트 첫 화면](../README.md)으로 돌아가기.

이 문서는 이번 개발의 목적을 고정합니다. 아래 네 가지를 위해 기존 구현을 보완하고 점진적으로 업데이트합니다. 기존 문서·화면과 충돌할 경우, 목표는 이 문서를 따르고 실제 동작은 코드·실기기 결과로 확인합니다.

## 1. 확정한 네 가지

| 항목 | 확정한 방향 |
|---|---|
| AI 탐지 유지 | 전용 실측 데이터가 없으므로 테스트 휴대폰으로 유사 행동과 자연스러운 태깅 행동을 수집한다. 규칙과 모델을 함께 사용하며 실측·피드백으로 개선한다. |
| NFC 동작 제한 | 금융 결제 승인·취소가 아니라 NFC가 불필요하게 동작·응답하지 못하도록 소프트웨어적으로 제한한다. |
| UI/UX 보완 | 탐지 오류가 정상 사용을 방해하지 않도록 모바일 담당자가 상태 안내와 해제·재시도 흐름을 보완한다. |
| 위치 로그 | NFC 이벤트와 제한·해제의 시각·위치를 기록한다. 어느 정확도까지 필요한지는 실기기 측정으로 정한다. |

카드사/FDS 연동, 금융 거래 취소·환급, iOS 동시 확장은 이번 범위에서 제외합니다.

## 2. NFC 제한이 뜻하는 것

이 문서에서 “NFC 차단”은 **NFC 통신 동작·응답을 소프트웨어적으로 제한한다는 목표**입니다. 센서를 물리적으로 파손하거나 금융기관의 거래를 취소하는 기능이 아닙니다.

현재 `NfcGuardHceService`는 판단과 업로드를 비동기로 처리하고 APDU에는 즉시 응답합니다. `ProtectionSettings`는 탐지와 센서 수집의 활성화 여부를 저장합니다. 둘 다 NFC 제한 구현이 완료됐다는 근거는 아닙니다.

따라서 다음 두 가지를 먼저 실기기로 확인합니다.

- 앱이 실제로 관찰할 수 있는 NFC 이벤트: 자체 HCE AID, 폴링 프레임 등.
- 앱이 실제로 제한·복구할 수 있는 NFC 경로: 필요한 API·권한·지원 기기·전면/백그라운드 조건.

일반 앱의 NFC 제어는 OS와 권한 조건에 영향을 받습니다. 예를 들어 리더 모드에는 전면 Activity 조건이 있고, 전체 NFC 켜기·끄기 API에는 별도 권한 제한이 있습니다. 어떤 경로를 사용할지는 검증 후 정하며, 현재 문서가 임의의 지갑이나 모든 기기에서 차단을 보장하지는 않습니다.

참고: [NfcAdapter 공식 API](https://developer.android.com/reference/android/nfc/NfcAdapter), [HCE 서비스 선택 구조](https://developer.android.com/develop/connectivity/nfc/hce).

## 3. 데이터 수집과 AI·규칙 결합

### 수집 방식

실험용 휴대폰에서 측정을 시작하고 자연스럽게 태깅·결제합니다. 일상에서 하지 않을 특정 모션을 강요하지 않습니다.

대표 조건은 주머니 위치, 가방 적재 정도, 이동·정지, 리더 높이·접근 방향, 기기별 태그 위치, 미숙한 태깅과 재시도입니다. 처음부터 조건을 1% 단위로 모두 나누지 않고 대표 조건을 먼저 측정합니다. RFID 차폐 파우치처럼 통신 성립 자체에 영향을 주는 조건은 별도로 확인합니다.

의도적 태깅과 비의도 접촉 모사는 가능한 한 동일한 장비·환경 조건에서 비교합니다. 실제 결제와 모사 통신은 출처를 구분합니다. 모델을 적용해 보지 않은 조건은 일부를 실측해서 일반화 여부를 확인합니다.

### 라벨과 결과의 의미

- `confirmed_intentional=true`: 사용자가 의도한 태깅.
- `false`: 사용자가 의도하지 않았다고 확인한 접촉 또는 해당 통제 실험.
- `null`: 아직 확인하지 못함.
- 사용자 응답, 통제 실험 라벨, 실제 결제 결과는 같은 증거가 아니므로 출처를 남깁니다.
- 패턴 이탈이나 높은 내부 점수를 실제 공격 확률로 단정하지 않습니다.

### 모델 경로

현재 개발 브랜치는 선형 가속도·자이로 6축을 96포인트로 보간하고, HAR 백본 고정 + 분류 헤드 학습 후 TFLite로 배포하는 코드를 갖고 있습니다. 모델이 없거나 로드하지 못하면 규칙으로 판단합니다.

이는 후보 구현입니다. 실제 백본·시간창·측정 주기·단위·정규화 적합성을 확인하고 규칙 및 다른 모델과 비교합니다. Python 학습과 Android 추론의 전처리는 반드시 같은 규격을 사용합니다. 기존 코드는 인덱스 보간이므로 타임스탬프 보간으로 바꾸려면 양쪽을 함께 수정해야 합니다.

기존 로컬 ML 실험 수정이나 이슈의 제안은 이 브랜치에 자동 반영된 것으로 보지 않습니다. 학습·평가 데이터 분리와 라벨 출처 처리는 별도 검토·반영합니다.

## 4. 제한 때문에 불편하지 않은 UI/UX

모바일 담당자가 아래 흐름을 보완합니다. 세부 화면과 유지 시간은 구현·실험 후 확정합니다.

| 상황 | 화면·동작 기준 |
|---|---|
| 정상 감지 상태 | 탐지가 실행 중인지와 NFC가 실제 제한 중인지를 구분해 보여준다. |
| NFC 제한 발생 | 제한 이유와 현재 상태를 짧게 표시하고, 사용자가 제한을 해제·재시도할 경로를 제공한다. |
| 정상 사용이 잘못 제한됨 | 복구에 걸리는 시간과 단계 수를 줄이고, 사용자 응답을 개선 자료로 남긴다. |
| 권한 부족·기능 미지원 | 제한이 적용되지 않았는데 적용됐다고 표시하지 않는다. |
| 앱 재시작·설정 변경 | 실제 적용 상태와 화면 표시가 일치하는지 확인한다. |

“사용자가 불편하지 않게 한다”는 목표이며 불편이 0이라고 보장하는 표현은 쓰지 않습니다. 정상 태깅 오탐, 해제 성공 여부, 재시도 시간 등을 실측해 개선합니다.

기존 UI 참고: [라이트·다크·온보딩 캡처](images/nfc-guard-ui-reference.png). 과거 시안이므로 위치 화면이나 NFC 제한 완료 상태를 보여주는 이미지는 아닙니다.

## 5. 위치가 포함된 로그

### 확정 요구와 아직 정하지 않은 것

**확정:** 이벤트 시각과 위치를 함께 확인할 수 있게 합니다. 예상하지 않은 장소에서 발생한 기록을 사용자가 확인하는 데 사용합니다.

**미정:** 목표 정확도 수치, 위치를 구하는 시점·대기 시간, 배터리 비용, 권한 요청 흐름. 정확한 매장·결제 단말 위치까지 알 수 있다고 약속하지 않습니다. 길거리라는 위치 정보만으로 결제 발생이나 공격 여부를 확정하지 않습니다.

### 구현할 필드 초안

현재 Android·서버에는 아래 위치 필드가 없습니다. 다음 목록은 추가 구현 제안이며 기존 API 계약이 아닙니다.

| 필드 | 의미 |
|---|---|
| `eventTime` | NFC 이벤트 또는 제한·해제 동작 발생 시각 |
| `latitude`, `longitude` | 확보한 위치 좌표 |
| `accuracyMeters` | 위치 제공자가 반환한 수평 정확도 반경. 절대 오차 상한이 아님 |
| `locationMeasuredAt` | 위치가 실제 측정된 시각. 이벤트 시각과 구분 |
| `locationStatus` | 확보 / 대략적 위치 / 오래된 위치 / 권한 없음 / 확보 실패 등 |

위치가 없으면 없음으로 표시합니다. 마지막 위치를 이벤트 발생 위치로 조용히 대체하지 않습니다. 대략적 위치만 허용되거나 실내·지하에서 위치 품질이 낮은 경우도 기록과 화면에서 구분합니다.

### 정확도 결정 방법

먼저 요구 수준을 **어느 주변 구역에서 발생했는지 확인하는 정도**로 놓고, 실외 도로·편의점 실내·지하철/버스에서 기준 위치와 측정값·정확도 반경·지연을 비교합니다. 그 결과로 목표 수치와 허용 대기시간을 정합니다.

위치는 사건 확인용 맥락으로 먼저 사용합니다. 위치 자체를 공격 확정 라벨로 사용하거나, 현재 센서 모델 입력에 바로 추가하지 않습니다. 이벤트 수집에 필요한 시점의 위치를 우선 검토하며 상시 이동 경로 추적은 이번 요구가 아닙니다.

참고: [Android 위치 권한과 정확도](https://developer.android.com/develop/sensors-and-location/location/permissions), [Location.getAccuracy](https://developer.android.com/reference/android/location/Location#getAccuracy()).

## 6. 코드·설명·화면을 같이 관리하는 기준

- 실행·설정은 [SETUP](SETUP.md), 현재 코드 흐름은 [ARCHITECTURE](ARCHITECTURE.md)를 따릅니다.
- README에는 목표와 코드 구현 상태를 구분해 표시합니다.
- 감지·제한·해제·위치 기록은 각각 실제로 검증한 조건을 남깁니다.
- 이전 KPI·R&R 문서는 과거 제안으로 보존합니다. 이번 네 가지 밖의 요구를 자동으로 추가하지 않습니다.
- 배포 설명에서도 시험 기능을 완성된 차단 기능이나 검증된 공격 확률로 표현하지 않습니다.
