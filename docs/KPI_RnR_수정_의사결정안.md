# NFC Guard KPI 및 R&R 수정 의사결정안

## 작성 목적

본 문서는 NFC Guard 프로젝트의 R&R(Role and Responsibility) 수정 여부를 판단하기 위한 간단한 KPI 초안이다.

핵심 목적은 다음과 같다.

- AI 파트를 1명이 아닌 2명으로 분리할 필요가 있는지 판단한다.
- 카드사/FDS 협력을 전제로 하지 않는 MVP 방향을 명확히 한다.
- 각 역할이 4개월 동안 어떤 결과물을 내야 하는지 최소 기준을 정한다.

## 전제

현재 프로젝트는 Android, 서버, ML 파이프라인의 스캐폴딩은 존재하지만, 실제 서비스 수준의 검증과 데이터는 부족한 상태다.

특히 AI 파트는 다음 요소가 아직 확정되지 않았다.

- 실제 NFC 태깅 센서 데이터셋
- 라벨링 기준
- 전처리 방식
- 전이학습에 사용할 공개 HAR 백본 또는 체크포인트
- ML/DL 적용 범위
- 성능 평가 기준

따라서 AI 파트는 단순 구현보다 조사, 설계, 데이터 관리, 모델 실험의 비중이 크다.

## MVP 방향 KPI

| KPI | 목표 기준 |
|---|---|
| 카드사 비의존형 MVP 설계 | 카드사/FDS 협력 없이 앱 자체 탐지, 사용자 확인, 경고, 데이터 축적이 가능한 구조를 문서화한다. |
| 2차 사용자 행동 제약 설계 | 의심 상황 발생 시 사용자 확인, 경고, 셀프 리포트, 후속 조치 안내 흐름을 정의한다. |
| 결제 직접 차단 가능성 검토 | 일반 Android 앱 권한에서 결제 흐름을 직접 차단하거나 허용 버튼으로 제어할 수 있는지 검토한다. |
| 대체 대응 흐름 설계 | 직접 차단이 어렵다면 알림, 사용자 확인, 카드 잠금 안내, 거래 확인 유도 등 대체 방식을 설계한다. |

## 권장 R&R

기존 `모바일 1 / 백엔드 2 / 연계 1` 구조보다 다음 구조가 더 적절하다고 판단한다.

```text
1. AI/Data 담당
2. AI/Model 담당
3. Mobile/Server 연동 담당
4. Backend/Security/PM 담당
```

이 구조의 의도는 AI를 하나의 단순 구현 파트가 아니라, 데이터와 모델을 분리해 병목을 줄이는 것이다.

## 역할별 KPI

### 1. AI/Data 담당

| KPI | 목표 기준 |
|---|---|
| 데이터셋 확보 전략 수립 | 공개 데이터셋, 자체 수집, 증강 데이터 사용 가능성을 비교한다. |
| 라벨링 기준 정의 | 정상 태깅, 의심 접근, 애매한 상황의 라벨 기준을 정리한다. |
| 입력 데이터 구조 정의 | 가속도계, 자이로, 시간창, 라벨 형식을 포함한 학습 입력 구조를 문서화한다. |
| 전처리 파이프라인 설계 | raw sensor data를 학습 가능한 형태로 변환하는 기준을 정한다. |
| 데이터 품질 관리 기준 작성 | 데이터 부족, 클래스 불균형, 잘못된 라벨링 문제에 대한 대응 기준을 정리한다. |

### 2. AI/Model 담당

| KPI | 목표 기준 |
|---|---|
| 전이학습 후보 조사 | HAR/UCI/HHAR 계열 모델 또는 체크포인트 후보 3개 이상을 비교한다. |
| 모델 구조 적합성 검토 | 프로젝트 센서 데이터 구조와 후보 모델의 입력 구조가 맞는지 분석한다. |
| ML baseline 모델 구축 | RandomForest, SVM, XGBoost 등 ML 기반 baseline 모델 1개 이상을 구현한다. |
| 전이학습 실험 | HAR 백본 또는 DL feature extractor 기반 실험을 1회 이상 수행한다. |
| 성능 평가 | Precision, Recall, F1-score, ROC-AUC, confusion matrix를 산출한다. |
| 오탐/미탐 분석 | 정상 태깅과 의심 상황에서 발생한 실패 케이스를 정리한다. |

### 3. Mobile/Server 연동 담당

| KPI | 목표 기준 |
|---|---|
| Android 실기기 테스트 | NFC/HCE 또는 대체 감지 흐름을 실기기에서 검증한다. |
| 사용자 확인 UI 구현 | "내가 한 태깅 / 의심됨" 선택 흐름을 구현한다. |
| 서버 API 호출 연동 | 모바일에서 이벤트 데이터를 서버로 전송한다. |
| 백그라운드 동작 범위 검증 | 앱이 백그라운드에서 처리 가능한 감지/알림 범위를 확인한다. |
| Google Play 심사 준비 항목 정리 | 권한, 개인정보 고지, 앱 설명 등 모바일 관련 심사 항목을 정리한다. |

### 4. Backend/Security/PM 담당

| KPI | 목표 기준 |
|---|---|
| 이벤트 수집 API 구현 | 모바일에서 전송한 의심 이벤트를 서버에 저장한다. |
| 라벨 확정 API 구현 | 사용자 확인 결과를 서버 데이터에 반영한다. |
| 학습 데이터 export 구현 | AI 파트가 사용할 JSONL 또는 CSV export 기능을 제공한다. |
| 기본 인증/인가 적용 | 무단 API 호출을 방지하는 기본 보호 구조를 적용한다. |
| 데이터 보호 정책 정리 | 센서/NFC 데이터의 수집 목적, 보관 기간, 삭제 기준을 문서화한다. |
| 통합 일정 및 산출물 관리 | 각 파트의 산출물, 회의 결정사항, 최종 보고서 흐름을 관리한다. |

## 공동 역할 KPI

다음 항목은 특정 1명에게만 맡기기보다, 모든 팀원이 각자 담당 파트 기준으로 함께 수행해야 한다.

| 공동 KPI | 목표 기준 |
|---|---|
| 문서 작성 | 각 담당자는 본인 파트의 설계, 구현 내용, 한계, 테스트 결과를 문서화한다. |
| API/데이터 명세 합의 | 모바일, 서버, AI가 사용하는 요청 형식, 응답 형식, 데이터 필드, 라벨 기준을 함께 확정한다. |
| 테스트 시나리오 작성 | 정상 태깅, 의심 접근, 이동 중 태깅, 주머니/가방 상황 등 실험 시나리오를 공동으로 정의한다. |
| 통합 테스트 참여 | 앱, 서버, AI 흐름이 실제로 연결되는지 각 담당자가 본인 파트 기준으로 검증한다. |
| 오탐/미탐 사례 기록 | 테스트 중 발생한 실패 케이스를 공통 양식으로 기록하고 원인을 분류한다. |
| 회의 의사결정 기록 | R&R, MVP 범위, 데이터 수집 방식, 모델 선택 등 주요 결정을 회의록에 남긴다. |
| 발표 및 보고서 기여 | 최종 발표자료와 보고서에 각 담당 파트의 결과와 한계를 반영한다. |

공동 역할은 별도 담당자가 모든 일을 대신하는 구조가 아니라, 각 파트 담당자가 자기 영역의 근거를 남기는 방식으로 운영한다.
최종 취합과 일정 관리는 `Backend/Security/PM 담당`이 맡되, 내용 생산 책임은 각 담당자에게 있다.

## 4개월 기준 마일스톤

| 기간 | 주요 목표 |
|---|---|
| 1개월차 | MVP 범위 확정, 카드사 비의존 구조 설계, R&R 확정, API/데이터 구조 정의 |
| 2개월차 | 모바일-서버 연동, 인증/인가 적용, 사용자 확인 UI, 학습 데이터 export 구현 |
| 3개월차 | 데이터 수집, 전처리, ML baseline, 전이학습 후보 실험 |
| 4개월차 | 통합 데모, 성능 평가, 오탐/미탐 분석, 최종 보고서 및 발표자료 완성 |

## R&R 수정 근거

AI 파트는 현재 실제 데이터, 전이학습 백본, 전처리 기준, 평가 방식이 모두 확정되지 않은 상태다.

따라서 AI를 1명이 담당하면 다음 위험이 있다.

- 데이터셋 조사와 모델 실험이 동시에 병목이 된다.
- 전처리 기준이 늦게 정해지면 서버 export 구조와도 충돌할 수 있다.
- 모델 성능 평가가 후반으로 밀리면 프로젝트의 핵심 근거가 부족해질 수 있다.
- 전이학습 후보가 프로젝트 입력 구조와 맞지 않을 경우 대안을 찾는 시간이 추가로 필요하다.

반면 모바일과 서버는 아직 검증과 보완이 필요하지만, 현재 스캐폴딩이 존재한다.
따라서 AI를 `Data`와 `Model`로 나누고, 모바일/서버/보안/PM을 통합 관리하는 구조가 4개월 일정에 더 적합하다.

## 회의용 요약

AI는 단순 모델 실행이 아니라 데이터셋 확보, 라벨링 기준, 전처리, 전이학습 후보 조사, 모델 실험, 성능 평가까지 포함한다.
따라서 AI를 1명에게 몰기보다 `AI/Data`와 `AI/Model`로 나누는 것이 일정 리스크를 줄인다.

또한 MVP는 카드사 협력을 전제로 하기보다, 앱 단독으로 가능한 위험 감지, 사용자 확인, 경고, 데이터 축적 구조를 목표로 잡는 것이 현실적이다.
